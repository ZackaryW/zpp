## Context

See `proposal.md` for motivation and the two capability deltas for accepted behavior. Today the workflow lifecycle mutates the packaged ZPP bundle immediately, native hooks are configured only through `zpp init`, and no owned model exists for OpenSpec-generated skills. OpenSpec 1.7.0 generates six core skills whose bytes differ for Codex, Pi, and Claude Code, so a shared generated projection would be incorrect.

The existing mutation layer already supports exact-content manifests, complete preflight, staged replacement, and rollback for the packaged ZPP bundle. The OpenSpec CLI is an external executable already used by ZPP's OpenSpec adapter.

## Goals / Non-Goals

**Goals:**

- Plan all selected hook, ZPP-bundle, and OpenSpec-skill effects before any persistent selected-agent mutation.
- Let OpenSpec generate its own current core skills without reading or changing the user's OpenSpec profile or project.
- Keep generated variants in agent-native destinations and maintain them by recorded generator version and exact owned content.
- Reuse the existing creation-plan and staged-removal transaction boundary.

**Non-Goals:**

- Package, transform, or normalize OpenSpec skill bodies inside ZPP.
- Install or upgrade the OpenSpec executable.
- Remove shared OpenSpec skills or independently usable native hooks with `workflow remove`.
- Guess that a historical shared `.agents/skills` projection belonged only to Pi; ambiguous historical projections remain untouched while Pi begins using `.pi`.

## Decisions

### Generate in an isolated TEMP project

Create a unique temporary directory through the standard-library temporary-directory API and set its OpenSpec configuration root inside that directory. Invoke the installed OpenSpec CLI noninteractively for all selected agents with the core profile, validate the generated layout, read the selected generated files into memory, and close the temporary directory on every exit path.

This preserves OpenSpec as content authority and is platform-neutral. Generating directly into a destination was rejected because it would expose partial writes and let OpenSpec create project artifacts in a user's repository. Reimplementing OpenSpec templates was rejected because it would drift from the installed version.

### Keep generated variants in agent-native roots

Use the generated tool variant without cross-agent substitution:

- Codex: `.codex/skills` for OpenSpec-generated skills; its packaged ZPP bundle remains in `.agents/skills`.
- Pi: `.pi/skills` locally and `.pi/agent/skills` globally for both its packaged ZPP bundle and OpenSpec-generated skills.
- Claude Code: `.claude/skills` for both bundles.

Although the skill names are the same, generated bytes differ across all three agents. Separate roots avoid collisions and preserve each tool's invocation syntax. Historical shared `.agents/skills` content is not removed merely because Pi now targets `.pi`, because the existing manifest cannot prove that Codex does not consume it.

### Track OpenSpec projections separately by version and content

Add a dedicated OpenSpec-projection manifest beside each generated projection. It records the selected agent, the detected OpenSpec version as a string or `null`, and the exact generated relative paths and digests. The `null` value is used only when generation succeeds but version detection does not yield a usable value.

An intact manifest plus matching files establishes managed ownership. Missing metadata with colliding OpenSpec skill names is unmanaged conflict. A changed digest without a version change is also conflict rather than permission to overwrite user edits. A changed detected version makes an intact projection outdated and eligible for regeneration during install or update. Equal recorded and detected values, including `null` and `null`, preserve the existing bytes.

Keeping this metadata separate from `.zpp-workflow-skills.json` avoids weakening that manifest's invariant that it owns only packaged `zpp-*` content. Removal retains the OpenSpec manifest with the shared skills so later installation or update can still verify ownership.

### Compose one preflighted workflow transaction

Split current workflow lifecycle work into planning and application. Planning loads the packaged ZPP bundle, prepares current native hooks, detects the OpenSpec version, generates only when required, validates every selected destination, and produces one composite creation/removal plan. Apply that plan only after every selected agent and surface passes preflight.

For install and update, native hooks are global even when the ZPP bundle is local. Repository-local OpenSpec generation participates only when the explicit opt-in is present. Removal applies only to the selected packaged ZPP projection and leaves hooks plus OpenSpec projections unchanged.

### Migrate only exact historical ZPP hooks

Maintain an explicit allowlist of complete hook records previously emitted by ZPP. Reconciliation may replace only an exact legacy record in its expected event. Commands that merely resemble ZPP, modified matchers, duplicate claims, or misplaced records remain conflicts. This repairs upgrades without turning a command prefix into ownership proof.

## Risks / Trade-offs

- **OpenSpec changes its generated layout or core set** → Validate generated skill directories and `SKILL.md` files before planning persistent writes; reject unsupported output atomically.
- **OpenSpec version detection fails while generation works** → Persist `null`; a later detectable version differs and triggers regeneration.
- **The external process is missing or generation fails** → Surface a domain error before persistent selected-agent mutation and clean the temporary project.
- **Codex and Pi were previously co-located** → Do not remove ambiguous `.agents` content; new Pi operations target `.pi` and leave historical cleanup explicit.
- **A user edits generated OpenSpec skills** → Exact manifest verification reports conflict and preserves the edits rather than overwriting them.
- **Planning becomes more expensive** → Skip isolated regeneration when an intact manifest records the same detected version; correctness and atomicity take precedence on first install or version change.

## Migration Plan

1. Introduce generated OpenSpec projection inspection and version metadata without changing existing destinations.
2. Add isolated generation and composite lifecycle planning behind the workflow commands.
3. Switch Pi's new workflow lifecycle target to its native `.pi` roots while preserving ambiguous historical `.agents` content.
4. Enable global OpenSpec bootstrap by default and local bootstrap only through the explicit opt-in.
5. Verify upgrade from exact historical ZPP hooks, rollback after late failures, and idempotent update with unchanged OpenSpec version.

Rollback removes the new product wiring while leaving any already generated OpenSpec skills and manifests intact as usable shared agent content; it does not destructively infer ownership of historical projections.
