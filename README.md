# ZPP 0.9.x

ZPP is a standalone profile and trait resolver for agent workflows. It composes
concise advisory traits from user and project layers, distributes its managed
workflow skills and native hooks, coordinates explicit repository codespaces,
and runs repository-owned affected verification without making Nx mandatory.

## Install

Install the ZPP command with [uv](https://docs.astral.sh/uv/guides/tools/):

```console
uv tool install git+https://github.com/ZackaryW/zpp.git
zpp --version
```

ZPP requires Python 3.10 or newer. The installed command is independent from
the optional governance plugins an agent application may load.

## Initialize ZPP and agent integrations

```console
zpp init
zpp init --agent codex --agent claude --agent pi
```

Initialization creates neutral user state without modifying the current project:

```text
~/.zpp/
├── global/
│   ├── config.json
│   ├── trait.json
│   └── traits/
├── profiles/
│   └── default/
│       ├── config.json
│       ├── trait.json
│       └── traits/
├── saved/
│   └── _bindings.json
└── cached/
```

With no explicit `--agent`, an interactive terminal offers Pi, Codex, and Claude
Code. Noninteractive initialization skips agent setup. Each selected agent
receives its complete current global integration: the twelve ZPP workflow
skills, version-matched generated OpenSpec core skills, and native lifecycle
hooks. Skill projections use the agent-native global roots documented below;
hooks use:

- Pi: `~/.pi/agent/extensions/zpp/index.ts`
- Codex: `~/.codex/hooks.json`
- Claude Code: `~/.claude/settings.json`

Initialization preflights every selected global destination before changing any
selected agent, preserves compatible projections, and refreshes intact outdated
managed projections. It does not install third-party plugins, instruction
paragraphs, repository-local integrations, or trust settings. Existing valid
user-owned default-profile content is not upgraded or rewritten during `init`.

## Install the standard workflow

ZPP's standard workflow has an independent lifecycle. A global installation is
one preflighted transaction that installs or reconciles all of the following for
each selected agent:

- the twelve permanent ZPP workflow skills;
- the agent's native ZPP lifecycle hooks;
- the OpenSpec core skills generated by the installed OpenSpec version; and
- missing packaged entries in the persistent `default` profile.

Existing same-name profile files, trigger values, configuration, custom traits,
and unrelated agent content remain user-owned.

```console
zpp workflow install --agent codex --agent claude --agent pi
```

Global workflow skills use each agent's native global location:

- Codex: `~/.codex/skills`
- Pi: `~/.pi/agent/skills`
- Claude Code: `~/.claude/skills`

Generated OpenSpec skills share the same Codex, Pi, and Claude Code roots listed
above. The workflow and OpenSpec manifests retain separate ownership even when
their projections share one directory.

Existing Codex workflow projections under `~/.agents/skills` are not migrated or
removed automatically. After upgrading ZPP, rerun the global workflow install to
create the managed bundle under `~/.codex/skills`.

For a repository-local installation, select local scope explicitly and optionally
provide its exact repository path:

```console
zpp workflow install --local C:\work\project --agent codex
```

A local installation normally projects only ZPP's workflow bundle. OpenSpec
skills are opt-in locally:

```console
zpp workflow install --local --with-openspec --agent codex --agent pi
```

Local ZPP workflow locations are `.agents/skills` for Codex, `.pi/skills` for
Pi, and `.claude/skills` for Claude Code. Opted-in OpenSpec skills use
`.codex/skills` for Codex and share the Pi and Claude Code roots. Global scope
is the default; `--global` is not accepted. A positional target is valid only
with `--local`.

A compatible global workflow normally supersedes a local installation. Use
`--force` only when the project intentionally needs its own ZPP projection.
`workflow update` maintains an explicitly selected managed scope. `workflow
remove` removes only ZPP-owned workflow paths; it leaves native hooks, shared
OpenSpec skills, profiles, and unrelated content installed.

For routine global maintenance after upgrading ZPP, use the option-free
`zpp update` command described below. It discovers installed managed workflows
and recognizable ZPP hooks across all supported agents, so agent selection is
not required.

## Repository-owned affected verification

Initialize an empty, committed verification mapping at the Git worktree root:

```console
zpp behave init
```

Edit `zpp.behave.yaml` to declare named commands, ordered targets, repository
impact globs, and either a typed argv provider or an Nx provider. ZPP validates
the mapping before starting a configured process. Provider-neutral argv values
are executed without a command shell, and changed paths never become executable
syntax.

Run the affected subset for a named command, compare exact revisions, or select
every declared target:

```console
zpp behave bdd
zpp behave bdd --base origin/main --head HEAD
zpp behave bdd --all
zpp behave bdd-audit --all
```

Local selection combines changes relative to `HEAD` with staged, unstaged, and
untracked non-ignored paths. A clean change is a successful no-op. Any changed
path that cannot be mapped conclusively selects all targets conservatively.
`--base` and `--head` must be supplied together. Complete execution and an
uncached or provider-specific audit remain separate repository commands.

Nx is optional. When a command explicitly selects the Nx provider, ZPP prefers
the repository's `node_modules/.bin/nx` over `nx` on `PATH`, validates the
declared project/target surface, and invokes it without downloading Nx,
installing framework plugins, migrating the workspace, or enabling Nx Cloud.
Repositories without Nx use the provider-neutral argv path equally.

## Profiles, saved overrides, and local layers

```console
zpp profile create work
zpp profile copy default work
zpp profile list
zpp profile remove work --yes
zpp global activate work

zpp profile saved create personal C:\work\project
zpp profile saved list
zpp profile saved remove personal --yes

zpp local init
zpp local init src\package
```

The persistent, user-owned `default` profile contains the platform-neutral
standard traits. Initialization creates it only when absent and never reapplies
bundled content over an existing valid default. Global workflow install, global
workflow update, and top-level `zpp update` are the compatible maintenance
exceptions: they add only missing packaged trait files and trigger entries,
preserving every existing authored value and same-name file. Local workflow
operations and workflow removal never mutate it.

`zpp profile copy` copies authored profile bytes without copying cache state.
`zpp global activate` archives the prior global layer as a collision-safe
timestamped profile and copies the selected profile into global. Set
`ZPP_PROFILE` for a temporary, non-mutating profile layer after global state.
Saved overrides bind one reusable layer to one or more canonical existing
directories; the closest matching ancestor wins.

Repository and subfolder `.zpp` layers are opt-in and must be inside a Git worktree.

## Traits

Each trait is one Markdown file with YAML frontmatter:

```markdown
---
name: review-errors
description: Inspect the smallest relevant failure first
order: 100
config:
  useThis: true
skill_lookup:
  - error-review
---
Inspect the smallest relevant failure output before changing implementation.
```

`trait.json` owns activation. A rule can be conditionless or use one fixed `which` or `workspace_contain` condition:

```json
[
  {"trait": "review-errors"},
  {"trait": "python", "workspace_contain": ["**/*.py"]},
  {"trait": "git-tools", "which": "git"}
]
```

`config.json` controls trigger replacement and shallow per-trait configuration overlays:

```json
{
  "trait_overwrites": false,
  "traitsConfig": {
    "review-errors": {"useThis": false}
  }
}
```

The packaged default also contains inactive ecosystem guidance for Python,
TypeScript, and Flutter, including `bdd-structure-python`, `bdd-structure-ts`,
and `bdd-structure-flutter`. These traits have no packaged trigger: a user-owned
global, profile, saved, or repository layer must activate them explicitly. They
preserve the repository's runner choice and do not activate Nx or impose
Gherkin on TypeScript or Flutter projects.

## Resolve

```console
zpp resolve
zpp resolve C:\work\project
```

Resolution layers global, optional `ZPP_PROFILE`, the closest saved override, repository root, and nested `.zpp` directories toward the target. It emits complete effective Markdown documents on stdout. No active traits produces empty stdout.

Authored Markdown remains authoritative and byte-unchanged. Participating layers are compiled lazily into independent `traits.json` caches with certification sidecars; invalid or stale source never falls back to old trait output.

## Codespaces

ZPP codespaces are explicit machine-local claims used to coordinate related
Git checkouts and optional read-only references during OpenSpec work. They do
not merge branches automatically.

```console
zpp codespace lock . --read-only C:\work\shared --yes
zpp codespace list
zpp codespace status <id>
zpp codespace open <id>
zpp codespace activate <id>
zpp codespace unlock <id> --yes
zpp codespace cleanup <id>
```

Mutating lifecycle operations preserve dirty or user-owned work. Explicit
worktree reconciliation remains a separately invoked workflow skill rather than
an implicit part of locking, opening, unlocking, or cleanup.

## Update

Upgrade the executable externally, then reconcile initialized global ZPP state
and every installed integration:

```console
uv tool upgrade zpp
zpp update
```

`zpp update` requires initialized user state and accepts no agent, scope,
target, force, or installation option. It additively refreshes the persistent
`default` profile, updates every discovered managed global workflow bundle,
maintains its native hook and version-aware generated OpenSpec skills, and
reconciles recognizable hook-only integrations. It leaves absent workflows,
repository-local projections and `.zpp` layers, caches, plugins, and unrelated
agent content untouched. Conflicting owned state rejects the complete update
before any write.

The command does not upgrade the running executable. Agent plugins retain their
own installation and update lifecycles. Use `zpp workflow update --local` only
for an explicitly selected repository-local managed workflow; `--global` is not
accepted, and a bare positional target is rejected.

## Development

```console
uv sync --all-groups
uv run scripts/bump_version.py <X.Y.Z>
uv run pytest
uv run zpp behave bdd
uv run zpp behave bdd-audit --all
```

The standalone bump script is repository maintenance tooling, not an installed
ZPP command. It synchronizes `pyproject.toml` and `src/zpp/__init__.py`, then
regenerates `uv.lock`; failures restore all three files.

This repository's mapping exposes independent `features/core`,
`features/workflow`, and `features/codespaces` roots. The audit command runs
each root through its own Behave process so root-owned bindings remain isolated.
